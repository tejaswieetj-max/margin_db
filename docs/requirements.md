## Introduction

Margin DB is a full-stack DBMS course project scoped to a single corporation — Microsoft, with a focus on its Gaming division (Xbox, Game Pass, Call of Duty). Business events (product launches, promotions, pricing changes, seasonal spikes) drive two parallel forecasts: a business forecast (revenue and gross margin) and a database load forecast (storage growth, query degradation). Three demo accounts are provided — `analyst_demo`, `analyst_all`, and `engineer_demo` — and the system must demonstrate a complete end-to-end demo loop covering query detection, index recommendation, index application, and measurable performance improvement. The fixed stack is MySQL 8.0.18+, FastAPI + pyodbc (ODBC-only in the backend), React 18 + Vite, and Python 3.12.

## Glossary

- **System**: The Margin DB application as a whole, encompassing database, backend API, and frontend.
- **Analyst**: A user authenticated with the `business_analyst` MySQL role.
- **Engineer**: A user authenticated with the `db_engineer` MySQL role.
- **Business_Event**: A dated occurrence (e.g., Call of Duty launch, Game Pass promo, Black Friday, price change) that affects both revenue/margin forecasts and database load forecasts.
- **FACT_SALES**: The central partitioned fact table recording Microsoft Gaming sales transactions.
- **DB_Load_Forecast**: A projection of future storage consumption and query performance degradation driven by Business_Events.
- **Business_Forecast**: A projection of future revenue and gross margin driven by Business_Events.
- **Query_Monitor**: The backend component (app/telemetry.py) that runs EXPLAIN ANALYZE and inspects performance_schema to detect expensive queries.
- **Index_Recommendation**: A suggested index generated by sp_recommend_index for a flagged query execution.
- **ODBC_Layer**: The pyodbc + MySQL Connector/ODBC driver stack used exclusively in `backend/` for all database access.
- **ETL_Pipeline**: The collection of Python scripts in `etl/` that fetch, clean, and load data from external sources and synthetic generators.
- **Stored_Procedure**: A MySQL stored procedure callable via `{CALL sp_name(?, ?)}` syntax through the ODBC_Layer.
- **Event_Calendar**: The UI component that displays upcoming Business_Events and their projected DB and business impacts.
- **JWT**: JSON Web Token used for stateless authentication between the frontend and backend API.
- **Performance_Schema**: The MySQL built-in instrumentation database used to collect digest statistics (latency, rows_examined, no_index_used).
- **Synthetic_Data**: Fabricated rows generated by `gen_synthetic_sales.py`, always tagged with `is_synthetic = TRUE`.
- **Role**: A MySQL database role (`business_analyst` or `db_engineer`) controlling object-level privileges.
- **Stage_Report**: A Markdown file written to `docs/stage_N_report.md` summarizing what was built, commands run, test output, and open issues for a given project stage.
- **QUERY_PLAN_NODE**: A weak entity (PK: qe_id, node_id) storing one row per node of a parsed EXPLAIN ANALYZE tree, including operation type, pct_time, and parent linkage.
- **EXPLAIN_ANALYZE**: The MySQL `EXPLAIN ANALYZE` statement executed on the analyst's ODBC connection to obtain a per-node execution plan tree; parsed by the backend using indentation depth.
- **CONFLICT_LOG**: A table recording optimistic-lock conflicts on PRICING_RULE: captures stale_version, current_version, the attempting user, and a timestamp.
- **DB_SIZE_SNAPSHOT**: A table storing point-in-time storage measurements (data_mb, index_mb, row_count per table) populated by sp_snapshot_sizes() and the daily MySQL EVENT ev_snapshot_sizes.
- **PRICING_RULE**: A table defining product pricing rules; includes a `version` column (INT NOT NULL DEFAULT 1) used for optimistic locking.
- **svc_telemetry**: A MySQL service account with INSERT/UPDATE on QUERY_EXECUTION, QUERY_PLAN_NODE, INDEX_RECOMMENDATION, and EXECUTE on sp_recommend_index only; used by the backend telemetry layer.
- **SAVEPOINT**: A MySQL named savepoint within a transaction, used by sp_place_order to enable partial rollback to a known consistent state.
- **Invisible_Index**: A MySQL index created with `INVISIBLE` so it is not used by the optimizer by default; made visible only after performance testing confirms benefit, via sp_apply_index.

## Requirements

### Requirement 1: Role-Based Authentication and Authorization

**User Story:** As a user of the system, I want to log in with my MySQL username and password, so that I can access only the views and actions appropriate to my role.

#### Acceptance Criteria

1. WHEN a user submits a username and password, THE System SHALL authenticate by opening an ODBC connection as that MySQL username; if the connection succeeds, THE System SHALL determine the user's role from `SHOW GRANTS` and role membership, issue a signed JWT carrying the role claim with an expiry of 60 minutes, and store the credentials in an in-memory session map keyed by the JWT on the server side.
2. THE System SHALL NEVER write credentials to disk, logs, or any persistent store; credentials are held only in the server-side in-memory session map for the lifetime of the JWT.
3. WHEN a subsequent authenticated request arrives, THE System SHALL open its own ODBC connection as the authenticated MySQL user for that request, so that MySQL enforces object-level permissions — not application code.
4. THE System SHALL support the following demo accounts: `analyst_demo` (restricted to the Gaming segment), `analyst_all` (all segments), and `engineer_demo`.
5. WHEN a user submits a username or password that does not match a known MySQL account or for which the ODBC connection fails, THE System SHALL return an HTTP 401 response with an error message indicating the credentials are invalid and SHALL NOT issue a token.
6. IF a request carries a JWT that is expired, malformed, or absent, THEN THE System SHALL return an HTTP 401 response and SHALL NOT execute the requested database operation.
7. IF a user attempts to access an endpoint that does not match their role, THEN THE System SHALL return an HTTP 403 response.
8. THE System SHALL never store plaintext passwords in source code or in the database.

### Requirement 2: Least-Privilege Role Enforcement

**User Story:** As a security-conscious course evaluator, I want each MySQL role to have only the minimum permissions required, so that data is protected from unauthorized access at the database layer.

#### Acceptance Criteria

1. THE System SHALL grant the `business_analyst` role SELECT-only access to views `v_sales`, `v_financials`, `v_events`, and `v_forecast_business`, and no direct access to any underlying base table.
2. THE System SHALL define all `business_analyst`-accessible views with `SQL SECURITY DEFINER`, filtering rows to the caller's assigned segments via `USER_SEGMENT_MAP` and `SUBSTRING_INDEX(USER(), '@', 1)`.
3. THE System SHALL grant the `business_analyst` role EXECUTE on `sp_margin_decomposition`, `sp_forecast_business`, and `sp_update_pricing_rule` only.
4. THE System SHALL grant the `db_engineer` role SELECT on `QUERY_EXECUTION`, `QUERY_PLAN_NODE`, `INDEX_RECOMMENDATION`, `DB_SIZE_SNAPSHOT`, `CONFLICT_LOG`, `v_events_min`, and `v_forecast_database`; read access on `information_schema` and `performance_schema`; and EXECUTE on `sp_apply_index`, `sp_reject_index`, `sp_add_partition`, `sp_snapshot_sizes`, and `sp_forecast_database`.
5. THE System SHALL grant the `db_engineer` role NO access to `ORDERS`, `ORDER_ITEM`, `FACT_SALES`, `PRICING_RULE`, `QUARTERLY_FINANCIALS`, or any column containing revenue, price, cost, or device information.
6. THE System SHALL grant the `svc_telemetry` account INSERT and UPDATE on `QUERY_EXECUTION`, `QUERY_PLAN_NODE`, and `INDEX_RECOMMENDATION`, and EXECUTE on `sp_recommend_index` only; no other privileges are granted to this account.
7. WHEN `analyst_demo` queries `v_sales`, THE System SHALL return only rows belonging to the Gaming segment, and SHALL NOT return rows from any other segment.
8. WHEN `analyst_all` queries `v_sales`, THE System SHALL return rows from all segments for which the account has a USER_SEGMENT_MAP entry.
9. THE System SHALL set default roles for all accounts using `SET DEFAULT ROLE` and SHALL NOT use the root MySQL account from the backend at any time.
10. THE System SHALL provide `tests/test_roles.sql` that asserts all of the following denials: `analyst_demo` cannot SELECT from `QUERY_PLAN_NODE`; `analyst_demo` cannot SELECT from `INDEX_RECOMMENDATION`; `engineer_demo` cannot SELECT from `FACT_SALES`; `engineer_demo` cannot SELECT from `ORDERS`; and `analyst_demo` querying `v_sales` returns only Gaming-segment rows.

### Requirement 3: Database Schema and Reference Data

**User Story:** As a course evaluator, I want a well-structured normalized schema, so that I can verify the application of relational database design principles.

#### Acceptance Criteria

1. THE System SHALL create all schema objects (tables, indexes, constraints, views, routines, triggers, events) exclusively via SQL migration files executed in ascending numeric order, where migration files are named `01_ddl.sql` through `06_seed_reference.sql` and each file is idempotent with respect to re-execution against an already-migrated schema.
2. THE System SHALL define all tables in the following list with their specified primary keys, foreign keys, and notable column constraints:
   - `COMPANY_SEGMENT(segment_id PK, name)`
   - `PRODUCT(product_id PK, segment_id FK→COMPANY_SEGMENT, name, category, list_price)`
   - `DIM_DATE(date_key PK, full_date, year, quarter, month, is_black_friday, is_holiday)`
   - `DIM_DEVICE(device_id PK, platform ENUM('Xbox console','Windows PC','Mac','Mobile','Cloud'), device_family, oem NULL — populated only for Windows PC rows)`
   - `DIM_REGION(region_id PK, name)`
   - `DIM_CHANNEL(channel_id PK, name)`
   - `ORDERS(order_id PK, order_date, device_id FK→DIM_DEVICE, region_id FK→DIM_REGION, channel_id FK→DIM_CHANNEL, status)`
   - `ORDER_ITEM` — weak entity, composite PK `(order_id, line_no)`, owner ORDERS: `order_id FK→ORDERS`, `product_id FK→PRODUCT`, `qty`, `unit_price`, `discount`, `unit_cost`
   - `FACT_SALES` — partitioned, composite PK `(sale_id, sale_date)`: columns `sale_date`, `product_id`, `segment_id`, `device_id`, `region_id`, `channel_id`, `event_id NULL`, `qty`, `gross_amount`, `discount_amount`, `cost_amount`, `is_synthetic`; NO foreign key constraints (MySQL restriction on partitioned tables); referential integrity enforced via BEFORE INSERT trigger
   - `PRICING_RULE(rule_id PK, product_id FK→PRODUCT, rule_type, value, version INT NOT NULL DEFAULT 1, updated_by, updated_at)`
   - `BUSINESS_EVENT(event_id PK, event_type, name, start_date, end_date, expected_lift, source_url)`
   - `EVENT_WINDOW_DAY` — weak entity, composite PK `(event_id, day_offset)`, owner BUSINESS_EVENT: `players_index`, `lift_ratio`
   - `QUARTERLY_FINANCIALS` — PK `(fiscal_year, fiscal_quarter, segment_id)`: `revenue`, `cogs`, `operating_income`, `source`
   - `STEAM_PLAYER(app_id, obs_date, avg_players, peak_players)`
   - `FORECAST(forecast_id PK, kind ENUM('business','database'), event_id, created_at, created_by)`
   - `FORECAST_LINE` — weak entity, composite PK `(forecast_id, line_no)`, owner FORECAST: `metric`, `period`, `value`
   - `QUERY_EXECUTION(qe_id PK, db_user, digest_text, started_at, duration_ms, rows_examined, rows_sent, flagged)`
   - `QUERY_PLAN_NODE` — weak entity, composite PK `(qe_id, node_id)`, owner QUERY_EXECUTION: `parent_node_id`, `operation`, `table_name`, `pct_time`, `est_rows`, `actual_rows`
   - `INDEX_RECOMMENDATION(rec_id PK, qe_id FK→QUERY_EXECUTION, table_name, columns_csv, status ENUM('proposed','testing','approved','rejected','applied'), before_ms, after_ms, decided_by, decided_at)`
   - `DB_SIZE_SNAPSHOT(snap_id PK, taken_at, table_name, data_mb, index_mb, row_count)`
   - `CONFLICT_LOG(conflict_id PK, rule_id, attempted_by, stale_version, current_version, at)`
   - `USER_SEGMENT_MAP(db_user, segment_id)`
   - `AUDIT_LOG(audit_id PK, table_name, action, old_value, new_value, db_user, at)`
3. THE System SHALL define `FACT_SALES` with `PARTITION BY RANGE (TO_DAYS(sale_date))` containing at least 8 named quarterly partitions covering the data date range plus a `MAXVALUE` catch-all partition; no foreign key constraints SHALL be defined on `FACT_SALES` (MySQL restriction on partitioned tables); referential integrity for `product_id` and `segment_id` on `FACT_SALES` SHALL be enforced by a BEFORE INSERT trigger.
4. THE System SHALL define three weak entities with composite primary keys: `ORDER_ITEM` with PK `(order_id, line_no)`, `QUERY_PLAN_NODE` with PK `(qe_id, node_id)`, and `FORECAST_LINE` with PK `(forecast_id, line_no)`.
5. THE System SHALL enforce referential integrity via foreign key constraints on all tables other than `FACT_SALES`, such that any attempt to insert or update a row with a non-existent foreign key value is rejected with a constraint violation and no partial write is committed.
6. WHEN a migration script encounters a DDL error, THE System SHALL halt on that file, log the failed filename and error message, and SHALL NOT attempt to execute any subsequent migration files.
7. WHEN `06_seed_reference.sql` is executed, THE System SHALL populate all reference and dimension tables with their complete seed data sets before any ETL script reads from those tables, such that any ETL script executed immediately after migration completes finds at least one row in each seeded dimension table.
8. WHERE `performance_schema` is enabled, THE System SHALL rely on `performance_schema` for digest-level statistics and SHALL NOT disable or alter its configuration.

### Requirement 4: ETL Pipeline — Data Acquisition and Loading

**User Story:** As the project owner, I want real-world data loaded from authoritative sources, so that business forecasts are grounded in verifiable facts.

#### Acceptance Criteria

1. WHEN `fetch_edgar.py` completes successfully, THE ETL_Pipeline SHALL have loaded at least one financial statement record per requested fiscal period into `QUARTERLY_FINANCIALS`, with each record traceable to a SEC EDGAR filing CIK and accession number; only quarterly (non-cumulative, non-annual) values for Revenue, Cost of revenue, and Operating income are loaded; restatements are deduped by retaining the latest-filed value; and any missing quarters are printed to stdout.
2. WHEN `load_steam.py` runs, THE ETL_Pipeline SHALL load daily player counts from `steam_players.csv` (columns: app_id, obs_date, avg_players, peak_players) into `STEAM_PLAYER`, then compute `EVENT_WINDOW_DAY` rows for each Business_Event covering day offsets −14 through +30 relative to `event start_date`, where `lift_ratio` equals the players value for that day divided by the average of `avg_players` over the 14 days preceding the event start.
3. WHEN `load_trends.py` runs, THE ETL_Pipeline SHALL load Google Trends data for the keywords "Call of Duty", "Game Pass", and "Xbox price", covering a date range of no less than 12 months prior to the load date; IF the pytrends API returns a rate-limit error, THEN THE ETL_Pipeline SHALL accept a manually supplied CSV as a fallback.
4. WHEN `load_events.py` runs, THE ETL_Pipeline SHALL validate each row in `events.csv` and reject any row where `source_url` is absent or empty or where `end_date` is earlier than `start_date`, logging the row identifier and the failing field for each rejected row; valid rows are loaded into `BUSINESS_EVENT`.
5. WHEN `segments.csv` is loaded, THE ETL_Pipeline SHALL reject any row where `fiscal_year`, `fiscal_quarter`, `segment`, or `revenue` is absent, logging the row identifier and missing field name for each rejected row.
6. WHEN `gen_synthetic_sales.py` runs, THE ETL_Pipeline SHALL generate 2–5 million rows for `FACT_SALES` (plus matching `ORDERS` and `ORDER_ITEM` rows for a 100,000-row subset) with `is_synthetic = TRUE`; for each real fiscal quarter × segment combination, generated gross amounts SHALL be scaled so their sum equals `QUARTERLY_FINANCIALS.revenue` for that combination within 0.1%; a reconciliation report comparing synthetic to real totals per quarter per segment SHALL be printed at end of run; the random number generator SHALL be seeded for reproducibility; and output SHALL be written as CSV chunks to `data/clean/` for bulk loading.
7. WHEN `load_sales.sh` is executed, THE ETL_Pipeline SHALL invoke `gen_synthetic_sales.py` and each loader script in a defined sequence, completing the full load within 30 minutes under normal network conditions.
8. THE ETL_Pipeline SHALL use `mysql-connector-python` only inside `etl/` scripts, and no file under `backend/` SHALL import `mysql-connector-python` directly or transitively.
9. IF an ETL script encounters a data source that is unavailable or returns a non-successful response, THEN THE ETL_Pipeline SHALL log the failure with a UTC timestamp and the source URL, SHALL exit with a non-zero status code, and SHALL NOT commit any partial data from that source to the database.
10. IF any individual loader script in the `load_sales.sh` sequence fails, THEN THE ETL_Pipeline SHALL halt the remaining sequence, log which script failed and at what sequence position, and SHALL NOT invoke subsequent scripts in that run.
11. WHEN `load_sales.sh` completes the data load, THE ETL_Pipeline SHALL run the heavy demo query against `FACT_SALES` without any secondary index on `(product_id, sale_date)` and verify that EXPLAIN shows a full table scan and the query takes over 3 seconds to execute; IF the query completes in under 3 seconds, THEN THE ETL_Pipeline SHALL print a warning instructing the operator to increase the row count or adjust the query before proceeding.
12. THE ETL_Pipeline SHALL require the operator to provide the following files and credentials before any data-acquisition script runs: `segments.csv`, `steam_players.csv`, `events.csv`, the MySQL Connector/ODBC installer for macOS matching the detected host architecture, and the MySQL root password for `.env`; THE System SHALL stop and describe exactly what is needed rather than fabricating or inferring these values.

### Requirement 5: Stored Routines, Triggers, and Scheduled Events

**User Story:** As a database engineer, I want business and maintenance logic encapsulated in MySQL server-side objects, so that the application enforces consistency at the database layer.

#### Acceptance Criteria

1. THE System SHALL implement all procedural logic — including data validation, multi-table writes, and maintenance operations — as MySQL stored procedures, stored functions, or triggers defined in `sql/04_routines.sql` and `sql/05_triggers_events.sql`.
2. WHEN the backend invokes a stored procedure, THE ODBC_Layer SHALL call it using the `{CALL sp_name(?, ?)}` syntax with parameter binding, where each `?` placeholder maps to a procedure parameter in declaration order.
3. THE System SHALL define a MySQL EVENT `ev_snapshot_sizes` that calls `sp_snapshot_sizes()` on a daily schedule (event_scheduler=ON), updating DB_SIZE_SNAPSHOT for all tracked tables.
4. IF a trigger or event violates a MySQL 8.0 syntax or feature limitation, THEN THE System SHALL halt execution of the migration script before any schema change is applied and write a conflict description — including the object name, the offending syntax, and the MySQL 8.0 limitation violated — to the migration output log.
5. THE System SHALL NOT use Oracle PL/SQL syntax in any SQL file, including `DECLARE…EXCEPTION`, `DBMS_*` package calls, `:=` assignment operator, or `%TYPE`/`%ROWTYPE` attribute references.
6. WHEN the backend calls a stored procedure that does not exist in the database, THE ODBC_Layer SHALL return an error response indicating the routine name and SHALL NOT silently return an empty result set.
7. WHEN a trigger explicitly raises a SIGNAL, THE System SHALL roll back the triggering DML statement, preserve the state of all other tables as of the start of that statement, and return an error to the calling ODBC_Layer indicating which trigger fired and the SIGNAL message text.
8. IF a trigger encounters a runtime exception other than an explicitly raised SIGNAL, THEN THE System SHALL roll back the triggering DML statement, preserve the state of all other tables as of the start of that statement, and return an error to the calling ODBC_Layer indicating which trigger fired and the nature of the exception.

**User Story:** As a frontend developer, I want a documented REST API, so that I can wire UI screens to live data without writing raw SQL.

#### Acceptance Criteria

1. THE System SHALL expose the backend API via FastAPI running under uvicorn, with all source files located under `backend/app/`.
2. THE ODBC_Layer SHALL be the exclusive database access mechanism in `backend/`; no ORM and no `mysql-connector-python` imports are permitted in that directory.
3. THE System SHALL provide an `/analyst` router exposing: GET `/events`, GET `/margin?segment&period_a&period_b`, GET `/forecast/business/{event_id}`, POST `/sql`, PUT `/pricing/{rule_id}`, and GET `/my-queries`.
4. THE System SHALL provide an `/engineer` router exposing: GET `/workload`, GET `/slow-queries`, GET `/slow-queries/{qe_id}/plan`, GET `/index-recs`, POST `/index-recs/{id}/approve`, POST `/index-recs/{id}/reject`, GET `/partitions`, POST `/partitions`, GET `/capacity/forecast`, POST `/forecast/database/{event_id}`, and GET `/conflicts`.

6. IF any required connection environment variable is absent at process startup, THEN THE System SHALL terminate with a non-zero exit code and emit an error message identifying the missing variable name before accepting any incoming request.
7. THE System SHALL validate incoming request payloads and return HTTP 422 with field-level error details for any malformed request.
8. IF the ODBC_Layer cannot establish a database connection, THEN THE System SHALL return an error response indicating service unavailability without exposing internal connection details.
9. THE System SHALL expose an OpenAPI documentation endpoint (e.g., `/docs`) listing all available routes, expected request parameters, and response schemas.
10. THE System SHALL never run the backend process as the OS root user.
11. THE System SHALL enable CORS only for the Vite development origin and SHALL NOT allow cross-origin requests from other origins.

### Requirement 7: Query Monitoring, Telemetry, and Index Workflow

**User Story:** As a database engineer, I want the system to detect expensive queries automatically and manage index recommendations through a tested workflow, so that I can take corrective action without manually inspecting performance logs.

#### Acceptance Criteria

1. WHEN an Analyst submits a query, THE Query_Monitor SHALL execute `EXPLAIN ANALYZE` on the analyst's ODBC connection, parse the returned plan tree using indentation depth to determine node hierarchy, and insert one `QUERY_PLAN_NODE` row per node — capturing `operation`, `table_name`, `pct_time`, `est_rows`, `actual_rows`, and `parent_node_id` — into the database using the `svc_telemetry` ODBC connection.
2. THE Query_Monitor SHALL use `performance_schema` exclusively for digest-level statistics (latency, rows_examined, no_index_used) and SHALL NOT use `performance_schema` for per-node plan timing; per-node timing comes from `EXPLAIN ANALYZE` output only.
3. THE Query_Monitor SHALL insert the parent `QUERY_EXECUTION` row (including `db_user`, `digest_text`, `started_at`, `duration_ms`, `rows_examined`, `rows_sent`) via the `svc_telemetry` ODBC connection, storing the normalized digest text and not the literal query values.
4. WHEN a `QUERY_PLAN_NODE` row is inserted where `pct_time > 50` and the `operation` value indicates a full scan, THE Query_Monitor SHALL set `flagged = 1` on the parent `QUERY_EXECUTION` row and invoke `sp_recommend_index(qe_id)` via the `svc_telemetry` connection.
5. WHEN `sp_recommend_index(qe_id)` is called, THE System SHALL examine the flagged query plan, identify the filter or join columns from the full-scan node, create an Invisible_Index on the target table with status `'testing'`, and record the recommendation in `INDEX_RECOMMENDATION`.
6. WHEN an Invisible_Index has status `'testing'`, THE System SHALL measure performance by running the original query in a single session with `SET SESSION optimizer_switch='use_invisible_indexes=on'`, storing the result as `before_ms` (original) and `after_ms` (with invisible index) in `INDEX_RECOMMENDATION`.
7. WHEN an Engineer calls `POST /index-recs/{id}/approve`, THE System SHALL call `sp_apply_index(rec_id)` which sets the index VISIBLE and status `'applied'`, and SHALL return a confirmation indicating the index name and the table it was applied on.
8. WHEN an Engineer calls `POST /index-recs/{id}/reject`, THE System SHALL call `sp_reject_index(rec_id)` which drops the Invisible_Index and sets status `'rejected'`.
9. IF `sp_apply_index` or the underlying `ALTER TABLE … VISIBLE` statement fails, THEN THE System SHALL return an error message indicating the reason and SHALL NOT alter the `INDEX_RECOMMENDATION` status.
10. THE System SHALL expose the slow-query queue and associated Index_Recommendations through the `/engineer` router, returning all entries in descending order of `started_at`.
11. WHEN an Analyst reruns a query for which an approved index is now active, THE System SHALL record a new `QUERY_EXECUTION` row whose `duration_ms` is at least 50% lower than the `duration_ms` of the original flagged `QUERY_EXECUTION` row for the same digest.

### Requirement 8: Business Forecast

**User Story:** As a business analyst, I want to see revenue and margin projections driven by upcoming events, so that I can communicate financial expectations to stakeholders.

#### Acceptance Criteria

1. THE System SHALL compute Business_Forecast values (projected revenue in USD, projected gross margin in USD) for each Business_Event whose date is strictly after the current query timestamp as recorded in the Event_Calendar.
2. WHEN an Analyst queries the business forecast for a named Business_Event, THE System SHALL return: event name, event date, projected revenue impact (difference between projected and baseline revenue in USD), projected gross margin impact (difference between projected and baseline gross margin in USD), and confidence tier (low / medium / high), where confidence tier is determined by data coverage: high if ≥ 80% of required financial inputs are present, medium if 40%–79% are present, and low if fewer than 40% are present.
3. THE System SHALL derive forecast figures from real financial data loaded by the ETL_Pipeline and SHALL NOT use hardcoded numeric constants as forecast inputs.
4. IF no Business_Forecast data is available for the queried Business_Event, THEN THE System SHALL return an empty result set with an indicator that no forecast data exists for that event, without raising an error.
5. THE System SHALL surface Business_Forecast data through the `/analyst` router via GET `/forecast/business/{event_id}`.

### Requirement 9: Database Load Forecast

**User Story:** As a database engineer, I want to see storage and query performance projections tied to business events, so that I can plan capacity and maintenance windows in advance.

#### Acceptance Criteria

1. THE System SHALL compute a DB_Load_Forecast for each upcoming Business_Event, projecting: estimated additional rows in `FACT_SALES` (as a non-negative integer), estimated storage growth in megabytes (as a non-negative decimal rounded to two decimal places), and estimated days until storage utilization reaches 90% of allocated capacity (as a non-negative integer, or null if current utilization already exceeds 90%).
2. WHEN a Business_Event is projected to cause storage utilization to reach 90% within 30 calendar days, THE System SHALL display a warning entry for that Business_Event in the Engineer's dashboard, including the Business_Event name, projected date of 90% utilization, and current storage utilization percentage.
3. IF an active query's projected execution time under the forecasted load is at least 2× (100% higher than) its baseline execution time measured under current load, THEN THE System SHALL include that query's identifier and both its baseline and projected execution times in the DB_Load_Forecast response.
4. THE System SHALL expose DB_Load_Forecast data through the `/engineer` router, returning all forecasts for upcoming Business_Events ordered by event date ascending.
5. THE System SHALL recalculate DB_Load_Forecast projections on a scheduled basis using the MySQL EVENT defined in Requirement 5, and IF the recalculation fails, THEN THE System SHALL preserve the most recently successful DB_Load_Forecast values and surface an error indication in the Engineer's dashboard.

### Requirement 10: Event Calendar UI

**User Story:** As any authenticated user, I want a visual event calendar, so that I can understand how upcoming business events affect both revenue and database health.

#### Acceptance Criteria

1. WHEN an authenticated user navigates to the Event Calendar page, THE System SHALL fetch Event_Calendar data from the `/analyst` or `/engineer` API route and display all Business_Events, each showing the event name, date, and event type label.
2. WHEN an Analyst selects a Business_Event on the calendar, THE System SHALL display the Business_Forecast values associated with that event, including at minimum the forecasted revenue impact and forecast date range.
3. WHEN an Engineer selects a Business_Event on the calendar, THE System SHALL display the DB_Load_Forecast values associated with that event, and IF any forecasted storage utilization exceeds 80% of provisioned capacity, THEN THE System SHALL display a storage warning indicator for that event.
4. IF the API request to fetch Event_Calendar data fails, THEN THE System SHALL display an error message indicating the calendar could not be loaded and SHALL NOT display stale or previously cached event data as current.
5. THE System SHALL source all Event_Calendar data exclusively from the `/analyst` or `/engineer` API routes and SHALL NOT embed event data as static frontend constants.

### Requirement 11: End-to-End Demo Loop

**User Story:** As a course evaluator, I want to run the full demo loop from a single starting point, so that I can verify all major system capabilities in sequence.

#### Acceptance Criteria

1. WHEN an Analyst executes a query against `FACT_SALES` whose execution time exceeds 2 seconds or whose rows-examined count exceeds 100,000 rows, THE System SHALL complete the query and record its execution plan in the slow-query queue with `flagged = 1`.
2. WHEN the Engineer views the slow-query queue after step 1, THE System SHALL show the flagged query with its Index_Recommendation.
3. WHEN the Engineer approves the Index_Recommendation, THE System SHALL apply the index to the live database within 30 seconds, and the index SHALL be verifiable as present in `information_schema.STATISTICS`.
4. WHEN the Analyst reruns the identical query after step 3, THE System SHALL record a new `QUERY_EXECUTION` row whose `duration_ms` is at least 50% lower than the `duration_ms` recorded in step 1 for the same digest.
5. WHEN the Event_Calendar displays a Business_Event of type "game_launch", THE System SHALL show a DB_Load_Forecast warning stating the number of days until storage reaches 90% capacity and listing all queries whose projected execution time under forecast load is at least 2× (100% higher than) their current baseline execution time.
6. THE System SHALL provide a runnable test script at `tests/test_demo_loop.py` that executes and asserts all five steps above without manual intervention and completes within 120 seconds.

### Requirement 12: Optimistic Locking and Conflict Logging

**User Story:** As a business analyst, I want pricing rule updates to be safe under concurrent access, so that stale writes are detected and logged rather than silently overwriting newer data.

#### Acceptance Criteria

1. THE System SHALL define a `version` column (INT NOT NULL DEFAULT 1) on `PRICING_RULE`; each successful update via `sp_update_pricing_rule` SHALL increment `version` by 1.
2. WHEN `sp_update_pricing_rule(rule_id, new_value, expected_version)` is called, THE System SHALL execute `UPDATE PRICING_RULE SET value = ?, version = version + 1 WHERE rule_id = ? AND version = ?`; IF `ROW_COUNT() = 0`, THE System SHALL re-read the current version, insert a row into `CONFLICT_LOG` (stale_version = expected_version, current_version = re-read value, attempted_by = current MySQL user, at = UTC_TIMESTAMP()), and raise `SIGNAL SQLSTATE '45000'` with a descriptive message; IF `ROW_COUNT() = 1`, the update is committed.
3. WHEN `PUT /pricing/{rule_id}` is called with a JSON body containing `{new_value, expected_version}`, THE System SHALL return HTTP 200 with the updated record on success or HTTP 409 with the current version value in the response body on conflict.
4. THE System SHALL define triggers on `PRICING_RULE` for UPDATE and DELETE events that insert a row into `AUDIT_LOG` recording `old_value`, `new_value`, `db_user`, and `at` for each change.
5. THE System SHALL provide `tests/test_concurrency.py` that launches two concurrent threads, each submitting `PUT /pricing/{rule_id}` with the same `expected_version`; asserts that exactly one receives HTTP 200 and the other receives HTTP 409; and asserts that exactly one `CONFLICT_LOG` row is created for that `rule_id`.

### Requirement 13: Transactional Order Placement

**User Story:** As a backend engineer, I want order placement to be fully transactional, so that no partial data is ever committed when any step of the order fails.

#### Acceptance Criteria

1. WHEN `sp_place_order(...)` is called, THE System SHALL open a transaction and insert rows into `ORDERS`, then `ORDER_ITEM`, then `FACT_SALES`, each insert preceded by a named SAVEPOINT.
2. IF any insert into `ORDERS`, `ORDER_ITEM`, or `FACT_SALES` fails, THEN THE System SHALL ROLLBACK TO the savepoint established before that failing insert, log the error and the point of failure, and leave no partial rows in any of the three tables.
3. THE System SHALL make `sp_place_order` callable via the ODBC_Layer using `{CALL sp_place_order(...)}` with parameter binding.

### Requirement 14: Partition Management

**User Story:** As a database engineer, I want FACT_SALES to be range-partitioned and manageable via API, so that query partition pruning is demonstrable and new partitions can be added without downtime.

#### Acceptance Criteria

1. THE System SHALL define `FACT_SALES` with `PARTITION BY RANGE (TO_DAYS(sale_date))` containing at least 8 named quarterly partitions covering the data date range plus a `MAXVALUE` catch-all partition.

5. WHEN EXPLAIN is run on a query with a filter restricting `sale_date` to a single quarter, THE System SHALL show partition pruning — accessing one or two partitions at most, not the full partition set; this must be demonstrated after the Stage 2 data load is complete.

### Requirement 17: DB_SIZE_SNAPSHOT and Capacity Tracking

**User Story:** As a database engineer, I want historical storage snapshots and a capacity forecast, so that I can track growth trends and plan ahead.

#### Acceptance Criteria

1. WHEN `sp_snapshot_sizes()` is called, THE System SHALL read `information_schema.TABLES` and insert one row per tracked table into `DB_SIZE_SNAPSHOT` recording `table_name`, `data_mb`, `index_mb`, `row_count`, and `taken_at` set to UTC_TIMESTAMP().
2. THE System SHALL define a MySQL EVENT `ev_snapshot_sizes` that calls `sp_snapshot_sizes()` on a daily schedule with `event_scheduler = ON`.
3. BEFORE the first live snapshot run, THE ETL_Pipeline SHALL insert 90 days of `DB_SIZE_SNAPSHOT` rows using a plausible storage growth curve; these backfill rows SHALL be identifiable by their `taken_at` timestamps being earlier than the date of the first live snapshot run.
4. WHEN `sp_forecast_database(event_id)` is called, THE System SHALL take the growth trend from `DB_SIZE_SNAPSHOT` history, multiply the write rate by the event lift during the event window, apply a linear regression using SQL aggregate functions (`SUM`, `COUNT`), and write to `FORECAST` and `FORECAST_LINE` the projected number of days until storage reaches 90% of allocated capacity and the normalized query digests expected to degrade under the forecast load.
5. WHEN GET `/capacity/forecast` is called, THE System SHALL return the most recently computed DB_Size and capacity projections from `DB_SIZE_SNAPSHOT` and the latest `FORECAST` rows of kind `'database'`.
6. WHEN POST `/forecast/database/{event_id}` is called, THE System SHALL invoke `sp_forecast_database(event_id)` and return the newly written forecast lines.
7. WHEN GET `/conflicts` is called by an authenticated Engineer, THE System SHALL return all rows from `CONFLICT_LOG` in descending order of `at`.
